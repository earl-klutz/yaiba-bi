# テストデータ案（データ取り込み・前処理）

`異常系の棚卸.md` で洗い出した20項目を、3つのテストデータで効率よく検知するための案。
1つのデータでなるべく多くの異常系を起こし、どの異常系が出たかを判別できるようにする。
名前はすべて架空名とし、実ログ（個人情報を含む）は使わない。

## テストデータ案1：実ログの「癖」をすべて再現した小さな合成ログ

### どういったデータが欲しいか

実ログを短く縮めた、架空名の合成ログ（約10分・5人程度）。実ログで起きていた次の出来事を、それぞれ少なくとも1回含める。

- 最初は YAIBA のないワールドにいて、そこで何人かが参加・離脱し、その後 YAIBA のワールドへ移動する
- YAIBA のワールドに一度出てから入り直す（Version の行が2回）
- 入り直した人の ID が変わる。前に別の人が使っていた ID が、別の人に割り当てられる
- 入り直しの直後に、同じ ID・同じ秒の行が2行ある
- 参加・離脱の名前に `(usr_...)` が付いている
- 23:55 開始で、0時をまたぐ
- 離脱の記録がない人がいて、最後の行は書き込み途中で切れている

### なぜ欲しいか

棚卸しで「起こりやすさ：高（実ログで発生）」とした異常系は、どれも実ログでは同時に起きていた。
実ログそのものは個人情報を含むので使えない。そこで、同じ出来事を架空名で再現し、1つのファイルでまとめて確かめる。
正解（いつ・誰が・どこにいたか）を自分で決めて作るので、「期待値と違う」ことを行数や件数ではっきり判定できる。

### 検知する異常系

| 検知する異常系 | 分類 |
| --- | --- |
| No.1 / 18 途中でワールドを移動している（YAIBA のないワールドの参加・離脱が混ざる / 位置データと名前が一致しない） | 完全性 |
| No.2 同じワールドに入り直している | 完全性 |
| No.3 / 14 入り直した人の ID が変わる / 同じ ID が別の人に使われる | 完全性 |
| No.4 離脱の記録がないまま、ログが終わる | 可視化 |
| No.5 / 15 最後の行が書き込み途中で切れている | 完全性 |
| No.6 / 17 同じ ID・同じ秒に2行 | 完全性 |
| No.7 日付をまたぐ（`event_day` のずれ） | 値の誤り |

11項目（重なりをまとめると7点）。

## テストデータ案2：1か所だけ壊した小さなファイルのセット

### どういったデータが欲しいか

案1の正常部分（数十行）をもとに、壊し方を1種類ずつ変えたファイルを用意する。

1. 存在しないパス（ファイルを置かない）
2. 空のファイル
3. YAIBA のないワールドだけのログ
4. ログ以外のファイル（画像、Shift-JIS で保存したもの）
5. 1行だけ座標に文字列が入ったもの、1行だけありえない時刻が入ったもの
6. 位置の行だけのログ、参加・離脱の行だけのログ
7. 数値に nan / inf が入ったもの、is_vr が True/False 以外のもの
8. すべてのファイルの壊れた行に、目印となる架空名（例：`SecretName_テスト`）を入れておく

### なぜ欲しいか

棚卸しの「致命的」は、1つのファイルに複数入れると、最初の1つで処理が止まり、残りを確かめられない。そのため、1ファイルに1種類ずつにする。
壊れた箇所以外は案1と同じなので、「停止すべきでないのに止まった」（No.12）や「列名が生データのまま」（No.10 / 13）を、正常な結果と並べて判定できる。
目印の名前を入れておけば、エラーメッセージに名前が出ないか（No.19）も、同じ実行で確かめられる。

### 検知する異常系

| 検知する異常系 | 分類 |
| --- | --- |
| No.9 ログファイルがない | 致命的 |
| No.8 / 10 空のファイル / YAIBA のないワールドだけのログ（列名が生データのまま） | 致命的 |
| No.11 ログ以外のファイル | 致命的 |
| No.12 1行だけ値が壊れている（ファイル全体が読み込み失敗） | 致命的 |
| No.13 位置だけ、または参加・離脱だけのログ | 完全性 |
| No.16 不正な値が入る（nan / inf / is_vr） | 完全性 |
| No.19 ユーザー名がエラーメッセージに出てしまう | 機密性 |

8項目。

## テストデータ案3：案1を拡大した 100MB 超のログ

### どういったデータが欲しいか

案1と同じ構造で、人数と時間を増やしたログ（例：60人・12時間、120MB 程度）。
中身の規則（誰がいつ入り直すかなど）は案1と同じにする。名前はすべて架空名で、目印の名前も含める。

### なぜ欲しいか

棚卸しの No.20「100MB を超えるログを処理して止まる、または極端に遅くなる」を確かめるため。
メモリはファイルサイズの約16倍使うので、量を増やしたデータでないと検知できない。
案1を拡大して作るので、量が増えたときに行数や ID の数が期待どおりかも確かめられる（完全性の No.3 / 6 が規模で悪化しないか）。
また、出力ファイル（中間テーブル、ヒストグラムの CSV、実行ログ）に目印の名前が出ないかも確かめる（No.19）。

### 検知する異常系

| 検知する異常系 | 分類 |
| --- | --- |
| No.20 100MB を超えるログを処理して止まる、または極端に遅くなる | 可用性 |
| No.19 ユーザー名が中間テーブル・出力ファイルに出てしまう | 機密性 |
| No.3 / 6（規模が大きいときの再確認） | 完全性 |
